# Benchmarks

What Hatch actually sustains, measured against the code as it stands.

Every number here was produced by [`benchmarks/`](../benchmarks/) on one machine
(Apple M1 Pro, 10 cores; Docker Desktop Kubernetes, 3 nodes) running the whole
stack — Postgres, Redis, Kafka, six services, and the full observability stack —
alongside the load generator. **These are comparative numbers, not capacity
claims for real infrastructure.** What transfers is the shape of each curve and
the identity of each bottleneck; the absolute values do not.

Every run writes a markdown + json artifact to `benchmarks/reports/` (git-ignored:
these are local run output, regenerated by `make bench`).

## How it is measured

The pipeline is three stages with capacities an order of magnitude apart, so
they are measured separately. A single blended "N per second" would only ever
report the slowest stage and explain nothing.

Each scenario isolates one stage and de-throttles the others. Ground truth for
"did the work finish" comes from Postgres rows, not from a metric — a metric can
be stale, reset, or unscraped, and *"every row reached a terminal state"* is a
stronger claim than *"consumer lag hit zero"*, which only says the messages were
read. Throughput comes from the first and last terminal row's timestamps, which
excludes the load phase and is not smeared by the scrape interval.

Method details and the reasoning behind each choice are in
[`benchmarks/README.md`](../benchmarks/README.md).

## 1. Ingest is bound by bcrypt, and nothing else is close

`ClientAuth` runs `bcrypt.CompareHashAndPassword` on **every** authenticated
request ([middleware_auth.go:45](../internal/api/middleware_auth.go)). Nothing
caches it. At the default `BCRYPT_COST=12` that costs **260 ms of CPU per
request**, and the API pod is capped at **500m CPU** — half a core — so each
request occupies the pod for roughly 520 ms.

Predicted ceiling: `1 ÷ 0.52s ≈ 1.9 RPS`.

**Concurrency does not move it** (`BCRYPT_COST=12`):

| Load generators | Achieved RPS | Request p50 |
|---|---|---|
| 1 | 1.9 | 517 ms |
| 4 | 1.8 | 2.188 s |
| 16 | 1.8 | 6.195 s |

Throughput is flat while latency grows linearly with concurrency. That is the
signature of a serial CPU-bound resource: extra clients only queue.

**Changing the cost moves it, exactly as bcrypt's `2^cost` work factor predicts:**

| `BCRYPT_COST` | Achieved RPS | Request p50 | vs. previous |
|---|---|---|---|
| 12 (default) | 1.8 | 2.191 s | — |
| 10 | 7.2 | 507 ms | **4.00×** |
| 8 | 29.1 | 114 ms | **4.04×** |

Two cost steps is a 4× change in work, and throughput tracks it to two
significant figures. The ingest ceiling *is* bcrypt.

For scale, the other hash on the same request — the sha256 that makes
`api_key_lookup` indexable — costs **81.5 ns**. The two differ by a factor of
**3.2 million**.

> **The lever.** bcrypt's cost is deliberate for password storage, but an API key
> is a 32-byte random secret, not a human-chosen password: it has no dictionary
> to attack, so the work factor buys far less here than it does for passwords.
> The options are to cache verified keys for a short TTL, or to lower the cost.
> Neither changes anything else in the system. Note that the cost is embedded in
> each stored hash, so a change only affects newly created clients.

## 2. Delivery throughput is `replicas ÷ provider latency`

`processBatch` walks its rows **sequentially**, each blocking on the provider
send, and there is one processor goroutine per pod
([main.go:114](../cmd/delivery-worker/main.go)). With the mock provider at
150 ms + 0–49 ms jitter (≈174.5 ms mean), one pod should manage `1 ÷ 0.1745 ≈
5.7/sec`.

Measured, with all schedules maturing in a single wheel slot so the workers are
the only thing pacing the run:

| Replicas | Delivered/sec | Worker window | vs. linear |
|---|---|---|---|
| 1 | 5.63 | 71.0 s | — |
| 2 | 10.36 | 38.6 s | 92% |
| 4 | 20.95 | 39.6 s | 93% |
| 8 | 30.88 | 26.9 s | 69% |
| 12 | 48.86 | 17.0 s | 72% |

Scaling is ~93% efficient to 4 replicas, then degrades to ~70%. Part of the
8-replica dip is partition granularity: `emails.due` has 12 partitions, so at 8
consumers four of them own two partitions each and the busiest consumer sets the
window. Beyond that, the shared Postgres, Redis and the host's 10 cores are
absorbing the difference.

**`DELIVERY_BATCH_SIZE` (default 1000) does not affect throughput at all.** It
controls how many rows are fetched before being sent one at a time.

**The leaky bucket never engages.** `DELIVERY_PROVIDER_RATE_PER_SEC` defaults to
1000/sec per (client, vendor), against an achieved 5.6/sec per pod. It is
mathematically incapable of binding under this configuration.

### Provider latency is still the dominant term, even at 12 replicas

Holding replicas at 12 and changing only the mock's latency:

| Mock latency | Mean send | Delivered/sec |
|---|---|---|
| 150 ms | 174.5 ms | 48.86 |
| 50 ms | 74.5 ms | 111.72 |

Latency ratio **2.34×**, throughput ratio **2.29×**. Throughput scales inversely
with provider latency almost exactly, which means the sequential-send model still
governs at the top of the tested range — the falloff above 4 replicas is a
constant ~30% efficiency tax, not a different bottleneck taking over.

> **The lever.** Every one of these numbers is a statement about a *sequential*
> sender. Concurrency within a batch would decouple throughput from provider
> latency entirely — the change is confined to `processBatch`, and the
> idempotency and status-transition guards that make it safe are already in place.

## 3. End-to-end, at a load the API can accept, the SLA holds

Production defaults (`BCRYPT_COST=12`, 4 delivery-worker replicas), 200 schedules
with arrivals spread across wheel slots. Two independent runs:

| | Run 1 | Run 2 | Target |
|---|---|---|---|
| Created | 200/200 | 200/200 | — |
| Ingest RPS | 1.8 | 1.8 | — |
| **E2E p50** | **224 ms** | **213 ms** | ≤ 500 ms — PASS |
| **E2E p95** | **893 ms** | **886 ms** | ≤ 2 s — PASS |
| **E2E p99** | **979 ms** | **977 ms** | ≤ 30 s — PASS |
| Stranded rows | 0 | 0 | 0 — PASS |

Every quantile reproduces within 5%. Across every run in this document — several
thousand schedules — there were **zero failures, zero retries, and zero stranded
rows**; every schedule reached `delivered`.

Note what the p50 leaves: the mock provider alone accounts for ~174 ms of a
500 ms budget. A real provider at 300 ms would breach the p50 target on provider
latency alone, with the rest of the pipeline contributing nothing. The p50 target
is worth revisiting against the provider you actually intend to use.

## 4. Two things worth fixing, found by measuring

### The wheel spends 97% of its load time refreshing gauges

`appendEntry` calls `publishWheelGauges()` after every successful append, and
that calls `Wheel.Stats()`, which scans all 3600 slots
([pipeline.go](../internal/scheduler/pipeline.go)).

| Operation | Cost |
|---|---|
| `Wheel.Append` | 73 ns |
| `Wheel.Stats` | 2.72 µs (constant — it walks 3600 slots regardless of occupancy) |

The gauge refresh is **37× more expensive than the append it follows**. For a
poll of 100,000 schedules — the configured `SCHEDULE_CHANNEL_BUFFER`:

- appends: 100,000 × 73 ns = **7.3 ms**
- gauge refreshes: 100,000 × 2.72 µs = **272 ms**

**97% of wheel-loading time is spent recomputing a gauge nobody reads more than
once per scrape.** Publishing once per drained batch, or on the ticker, removes
it. This has not caused a problem — the poll is hourly and 279 ms is invisible —
but it is pure waste at a hot path, and it grows with the poll size.

### `provider_send_duration_seconds` cannot resolve provider latency

Its buckets step `.1 → .25 → .5`, and every mock send (150–199 ms) lands in the
single `(0.1, 0.25]` bucket. `histogram_quantile` therefore interpolates to a
constant **0.2425 s** in every run at every replica count, regardless of what
actually happened.

I initially read that constant as evidence of contention. It was not evidence of
anything — the metric is blind in exactly the range that matters, and typical
real-provider latency (100–300 ms) falls in the same blind spot. It needs
intermediate buckets around `.15/.2/.3` to be usable.

`e2e_latency_seconds` and `batch_duration_seconds` both have healthy spread and
are trustworthy.

worth optimising; the provider call is the only term that matters.
